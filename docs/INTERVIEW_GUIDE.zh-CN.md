## 3. 结构和技术选择

### 为什么选 SQLite

它不需要评审者额外安装数据库，启动后即可使用；又能提供跨连接、跨进程的事务锁，比只靠一个 Python 字典或进程内锁更容易解释重启和并发行为。WAL 允许读取和写入更好地共存，但 SQLite 仍然一次只有一个写者。

后端使用同步路由和标准库 sqlite3，因为项目没有复杂异步数据库需求。FastAPI 会把同步路由放在线程池执行。每个请求单独打开连接，线程之间不共享同一个 connection。

生产扩容时的变化不是“加更多 uvicorn worker 就行”：多个写者会争同一个 SQLite 写锁。高并发生产部署应考虑 PostgreSQL、行锁/条件更新、真实用户购物车隔离、预留到期释放和迁移管理。

### 为什么 React + Vite，为什么没有 Redux

只有一个商品详情流程，组件状态足够清晰。API 调用放在 api.ts，数据类型与规格解析放在 domain.ts，未确认操作恢复放在 pending.ts，交互放在 App.tsx。没有引入多页面路由或全局状态框架的必要。

TypeScript 在编译期约束代码，但不能保证网络返回的 JSON 符合类型。因此使用 Zod 在 API 边界做运行时校验，遇到畸形成功响应时拒绝把它当作可靠结果。

图片是项目内的 SVG 商品示意图，没有外部图片服务依赖。它们不是实际商品照片；商品文案、价格和库存都是虚构种子数据。

### 为什么不实现登录、支付和部署

题目把这些明确排除。当前所有浏览器共用一个演示购物车，是公开写明的简化；不能声称具备用户隔离。加购立即预留可用库存，没有到期释放或删除接口，因此数据持久化后反复测试可能售罄，需要按 README 重置演示数据库。

## 4. Task A：状态、校验与幂等

### 四个核心状态

- `on_hand`：仓库实际还有多少件。
- `reserved`：所有订单合计预留多少件。
- `orders[order_id]`：某订单预留多少件。
- `processed`：已经处理过的事件 ID。

始终满足：`reserved == sum(orders.values())`，并且 `0 <= reserved <= on_hand`。维护单独的 reserved 总数，是为了每条命令不必重新遍历所有订单求和。

假设初始库存 10，订单 a 预留 4：此时 on_hand=10、reserved=4、available=6。发货 2 后 on_hand=8、reserved=2、available 仍是 6。**发货不应再次减少可用库存**，因为它之前已经预留过。释放剩余 2 后 on_hand=8、reserved=0、available=8。

### 为什么业务拒绝也记录 event_id

题目明确要求。例子中的 e2 第一次因库存不足被拒绝，后来即使参数改成另一个订单和较小数量，仍然是 DUPLICATE。若拒绝不记录，重放会在库存变化后产生不同业务效果，破坏事件的确定性。

代码顺序：完整解析校验 → 检查重复 → 记录事件 ID → 检查/执行业务操作。这里“拒绝不能改变状态”指库存与订单不能改变；**合法业务拒绝更新 processed 是明确要求**。

格式错误如何处理，题目没有完整规定。实现选择 REJECTED 且不消耗事件 ID，校验优先于重复检查。这个假设写在 A/README.md；如果面试官期待不同规则，可以讨论并修改，而不是把自己的假设当成题目原文。

### 复杂度怎么回答

每条命令期望 O(1) 哈希操作，N 条期望 O(N)。最终 K 个未清订单排序为 O(K log K)。不要笼统声称“整个程序严格 O(N)”而漏掉排序，也不要把哈希表平均复杂度说成最坏情况保证。还要计入输入字节的解析成本；CLI 为了先验证命令总数，会缓存输入。

### 可当场演示

```sh
python -m pytest A -k rejected_event -v
python -m pytest A -k malformed -v
```

你应该能说清楚：第一组证明拒绝后的 ID 也不可再执行，第二组证明校验失败不会留下半次修改。

## 5. Task B：最容易被深入追问的算法

### 先讲目标，不要先讲代码

它不是“最低运费”。比较顺序是仓库数、费用、分配列表。一个仓库需要 1,200 元、两个仓库免费，也必须选一个仓库。测试 `test_count_beats_cost` 就专门验证这一点。

把结果写成 `(used_count, total_cost, [(id, qty), ...])`，按字典序比较。分配列表仅包含使用的仓库，quantity 按整数比较。全零槽位的固定长度向量不等价，可能错误地偏好跳过较早 ID。

### 为什么普通贪心不够

库存大的仓库有助于减少仓库数，但在最少仓库数量相同的情况下不一定最低价；单位运费低也可能有很高固定费。单看一个局部指标无法满足三层目标。

枚举仓库子集需要 2^W，W=30 时不可接受。枚举每个仓库分配的所有数量更大。题目 Q≤2000 提示以数量作为 DP 维度。

### 先推 O(WQ²)，再解释如何优化

仓库按 ID 排序。`D[i][q]` 表示仅用第 i 个及之后仓库，恰好分配 q 件时最好的 `(仓库数,费用)`。只有终点 `D[W][0]=(0,0)`，其余不可达。

不使用当前仓库：取 `D[i+1][q]`。使用 t 件：取后缀 `D[i+1][q-t]`，仓库数加 1，费用加 `fixed + t*unit`。

普通写法三层循环 i、q、t，约 O(WQ²)。令 `p=q-t`，把费用改写为：

```text
后缀费用[p] - p*unit + fixed + q*unit
```

对于固定的 q，后两项是常数，因此只需在 `p∈[q-stock,q-1]` 中选择最小的：

```text
(后缀仓库数[p], 后缀费用[p] - p*unit)
```

q 递增时这个区间左右端都向右移动，是滑动窗口最小值。用单调双端队列维护候选，每个 p 最多入队、出队各一次，得到每个仓库 O(Q)，总 O(WQ)。仓库数必须是比较键的第一项，不能只维护费用最小值。

### 单调队列为什么可以删掉尾部候选

新候选的比较键小于等于旧候选，且下标更大、过期更晚。在它们同时可用时，新候选不会更差；旧候选先过期，因此未来也不会反超。于是旧候选可以永久丢弃。这只负责“仓库数和费用”这两个数值目标，分配字典序单独恢复。

库存为 0 时窗口为空，所以不能收固定费、不能把它算作使用仓库。固定费为 0 也不能让“分配 0 件”算一个仓库。

### 为什么恢复过程要从小 ID 开始，t 从 1 开始

最优数值目标已知。对当前最小 ID，尝试 t=1、2、3……，检查“使用该数量 + 后缀最优结果”是否仍等于全局最优目标。

只要存在可行的正数 t，就优先使用这个较早 ID；否则只能跳过。使用它时选最小 t，第一对 `(ID,t)` 就最小。余下后缀递归执行同样规则。这里 t=0 不是最优先选项，因为列表不包含未使用仓库。

例子：A、B 各 12 件，单位费相同，无固定费，需求 13 件。必须用两个仓库，成本一样，结果是 A 1、B 12，而不是 A 12、B 1。

### 为什么保留所有后缀 DP 行

只算最优费用时可滚动数组到 O(Q) 空间；但这里要验证每一步分配是否能被后续仓库补成最优解。保存 O(WQ) 后缀状态让恢复逻辑直接、可证明，在 30×2000 规模下很小。没有为了省几十万个对象而把解释复杂化。

### 如何证明不是“跑了示例就觉得对”

`test_random_against_independent_exhaustive_oracle` 对 500 个固定随机种子生成的小实例，枚举所有数量组合，直接按三层目标选答案，再与 DP 比较。两个实现原理不同，能检测边界、窗口和平局错误。随机对照不是数学证明，所以 README 同时给出状态转移与恢复论证。

```sh
python -m pytest B -k 'random or lexicographic or maximum' -v
```

## 6. 后端：一次加购究竟发生什么

读取 `app/backend/main.py` 的 `add_item`，按下面的顺序讲：

1. Pydantic 严格校验 JSON 和 Idempotency-Key。数量字符串、布尔值、小数、额外价格字段都拒绝。
2. 用规范化 JSON 生成 payload fingerprint，忽略对象字段顺序和空白差异。
3. 打开本请求的 SQLite 连接，执行 `BEGIN IMMEDIATE`。
4. 查 key：同 payload 返回旧状态码/旧响应；不同 payload 返回 409。
5. 查 SKU。不存在则准备 404；存在则执行带库存下限条件的 UPDATE。
6. 更新成功时 upsert 购物车数量，并生成服务器价格计算的购物车快照；失败时返回库存不足和当时可用量。
7. 保存确定的业务结果到幂等表。
8. 提交事务后返回响应。任何异常导致库存、购物车和幂等记录一起回滚。

### 为什么要同一事务

如果先扣库存、后存幂等，中间崩溃，重试时找不到 key，会再次扣库存。反过来先存成功 key、后扣库存，中间崩溃会返回一个没有发生的成功。所以三类写入要一起成功或一起失败。

### 两个请求抢最后一件会怎样

请求 A 获得写事务后，B 等锁。A 检查、扣到 0、写购物车、写 key、提交。B 之后读到的是 0，条件 UPDATE 影响 0 行，返回 409。若 A 失败回滚，B 则仍可以成功。

同一个 key 的两个请求：第一个提交后，第二个看到幂等记录，返回旧结果。两次 HTTP 成功不代表执行了两次；真实购物车总数只增加 1。

测试使用两个独立 FastAPI 实例和独立 SQLite 连接，通过线程 barrier 同时发请求，不是“连续调用两次”冒充并发测试。

### 为什么不用 SELECT 之后直接 UPDATE

如果没有事务锁或条件更新，两个请求都可能读到 stock=1，然后各自认为能买。这里 BEGIN IMMEDIATE 在读取前序列化写者，条件 UPDATE 是第二层保障。Python 锁只覆盖当前进程，不能替代数据库级边界。

### 价格、购物车总数与幂等失败

价格由服务器 SKU 表决定，使用整数分避免浮点金额误差。`total_item_count` 是数量之和，不是 SKU 行数。

有效业务失败也缓存：某 key 因库存不足失败，补货后重放仍返回原失败。新的购买意图使用新 key。无效 JSON/字段校验在路由执行前拒绝，未消费 key；事务失败回滚的 5xx 也未消费 key。

请区分 App 和 Task A：A 按题目对同一 event_id 一律 DUPLICATE，即便参数变化；App 对同 key 不同参数返回 409，因为它是 HTTP API 幂等契约。它们不是完全相同的协议。

## 7. 前端：失败路径比按钮样式更重要

### 为什么不单独存 selectedSku

`selectedSku = resolveSku(product, selection)` 可由已有状态直接推导。若再存一个独立状态，切颜色时可能更新了选项却没更新价格或图片，形成旧 UI。当前商品、选项变化后统一推导 SKU。

### 为什么禁用按钮还要 ref

`setBusy(true)` 要等 React 渲染后按钮才真的 disabled。在这个窗口里可能收到第二次事件；同步写 `inFlight.current=true` 立刻封住窗口。它只改善本页面重复点击，无法保护网络重放、多个浏览器或服务器并发，所以后端幂等仍不可少。

### 超时不是失败证明

可能服务器已提交，响应在网络中丢失。前端此时若生成新 key，服务器无法知道它是重复请求，会再次加购。正确做法是保存 `{key, body}`，显示“结果未确认”，重试同一个 key 和同一个 payload。

当前代码也将 5xx 和畸形成功响应视为未确认；不允许用户在这个请求解决前切规格发新请求。sessionStorage 支持同一标签页重载恢复。存储不可用时仍可在内存中重试，但不能承诺关掉页面后恢复。

### 重放响应可能过时

第一次响应是库存 7、购物车 1 件。其后别的请求继续购买，再重放第一次请求时仍返回历史响应。因此确认加购后要重新 GET 商品和购物车，才能更新到当前状态。

刷新失败不应把已成功的加购显示成失败；否则用户可能再买一次。代码保留成功反馈，单独提示库存/购物袋刷新失败，并提供只读刷新按钮。`refreshGeneration` 防止旧刷新在新加购完成后晚到并覆盖状态。

### 必须能说明的无障碍措施

真实 button、fieldset/legend 和 input label；选项用 aria-pressed；购物袋开关有 aria-expanded；成功状态用 role=status，错误用 role=alert；有跳到主体链接和可见 focus；动画尊重 prefers-reduced-motion。移动布局在 760px 下改为单列。自动化 DOM 测试不等于屏幕阅读器或真实浏览器视觉验收，不能混为一谈。

## 8. Task C：六个可以被追问的判断

### OAuth 和租户不是一回事

connections 返回 200 说明该 token 能访问连接列表，不证明目标 tenant 一定在列表里，也不证明有 invoice scope。要匹配 tenantId，注意不能拿连接的 id 当 tenantId；再使用租户头访问 Organisation 验证租户作用域调用。该验证依赖 settings.read 权限，不能默默增加用户没有授权的 scope。

### 401、403、404 不要都“刷新 token 再试”

401 查 token、过期、撤销、错误凭据，最多协调刷新并重试一次；403 查权限/授权 scope；404 查路由、资源和所属租户。相同组织在不同环境出问题，可能是 worker 加载了另一套 app credential 或 tenant binding。Xero demo company 不是另一个随意拼出来的 API 域名。

### 2026 年的 scope 变化

本次核查的官方文档已经列出 accounting.invoices / accounting.invoices.read。旧 accounting.transactions 范围仍处过渡期，不应不加说明地复制旧 SDK 示例。这也是 C 明确要求当前官方文档的原因。

### 分页 checkpoint 不等于服务端快照

If-Modified-Since 固定本轮下界，按页写入时把数据与本地 checkpoint 一起提交；全部成功才推进 committed watermark。中途失败，重放同一下界的第一页，通过 `(tenant_id,InvoiceID)` upsert 去重。watermark 使用本轮开始时间，不用拿到的最大更新时间，避免跳过尚未读到的变更。

但服务端分页结果会随并发修改变化：重叠窗口能降低风险，不能数学上保证任意编辑下零遗漏。需要定期更广范围的 reconciliation、可选 webhook 提示和漏数告警。别把 page=3 当成永不变化的快照游标。

### 限流是调度问题

Retry-After 是最早重试时间，不能用一个 60 秒上限把更长的官方等待截断。共享配额、租户冷却和 app 全局预算要跨 worker 协调；一天配额用完应延后调度，不能让 worker 睡一天或立即无限重入队列。当前文档 Starter 日配额 1000，高档位 5000，不是所有应用都 5000。

### Xero 幂等只有六分钟

当前官方说明 key 响应缓存为六分钟，错误也可能被缓存。超出窗口重试旧 key 会被当新请求，可能重复创建。持久化内部 outbox 操作、请求 hash、首次发送时间、Xero key、InvoiceID，短窗口内原样重放；窗口外先 GET 核实，不能盲目再创建。Reference 不是唯一键；受控销售发票编号可以帮助查找，但要核对租户、类型、金额和业务映射。无法确定就保持 unknown 并人工处理。

另外，多个组织连接可能共享同一 OAuth grant。刷新锁应按 grant，而不是只按 organisation，否则两个组织的 worker 会竞争旋转同一 refresh token。

## 9. 现场调试练习

建议在练习分支做修改，先让测试失败，再定位和恢复。不要把故意破坏的版本提交。

### 练习 A：重复失败事件居然成功了

模拟删除 A 中 `self.processed.add(event)` 或把它移到只有成功时才执行。运行 `python -m pytest A -k rejected_event -v`。

定位顺序：看第一次响应 REJECTED → 检查 processed 是否含 e1 → 补货后重放 → 找到事件登记的时机。修复应恢复“合法业务请求不论成功失败都登记”，同时保证 malformed 测试不被误伤。

### 练习 B：B 能过示例，却选错同价方案

模拟恢复时把 t 改为从大到小，或先选择 skip。运行 `python -m pytest B -k lexicographic -v`。先列出两个具体候选分配，再按列表首个不同元素比较，避免只盯着 DP 费用值。

### 练习 C：购物车加了一件，但页面说失败

正常 POST 成功后，让产品刷新失败。`App.test.tsx` 中 “keeps confirmed success distinct from failed background refresh” 已覆盖。检查 POST 结果与后续 GET 是否错误地共用一个失败状态。修复方向是保留提交结果、独立显示刷新错误，不要重新 POST。

### 练习 D：库存扣了，但购物车没变化

后端 `test_failure_rolls_back_stock_cart_and_key` 用 SQLite trigger 在购物车写入时制造异常。运行：

```sh
python -m pytest app/backend/tests -k rolls_back -v
```

检查 HTTP 500 后库存是否回到 8、幂等表是否仍为空，解除故障后用同一个 key 能否成功。不能通过“异常时再手动加回库存”替代事务，因为补偿过程也可能失败。

### 练习 E：网络失败重试变成两件

看前端两次 `api.add` 调用的参数。若 key 不同，即便 body 一样，服务器也把它们当不同购买意图。已有测试会检查两次调用完全一致。浏览器 Network 面板也能查看 Idempotency-Key；不要把真正的第三方 token 放进调试截图。

### 通用调试表达

先说复现输入与预期，再说实际结果；形成一条可验证假设，选择最小测试；修复后同时跑相关成功路径和失败路径。比如“我怀疑 processed 登记在库存判断之后，因此拒绝事件没有被记住。我先检查这个集合，再执行重放测试”，比直接跳进随机改代码更有说服力。

## 10. 小需求修改演练

### 增加购物车删除/释放库存

首先明确删除是整行还是减少 n 件，是否需要幂等，释放到哪个库存字段。增加一个事务：验证该行已有量 → 减少/删除 cart item → available_quantity 增加 → 写幂等结果。必须保持“新增与释放不能制造负数或凭空增加库存”。测试重复删除、超量删除、并发删除/新增和失败回滚。

现有 idempotency 表只服务一个 POST 操作。扩展其他操作时，应把 method/path/cart_id 加入作用域或 fingerprint，避免同 key 在不同接口含义混淆。

### 增加 XL

如果仍是颜色/尺码两个维度，增加后端 SIZES 与对应 seed 行、图片，并调整尺码说明和测试。前端从 options 数组渲染，不应再写死一个 XL 按钮。已有数据库通过 INSERT OR IGNORE 增加新 SKU；如果改变旧 SKU 的价格或库存，当前 seed 不会覆盖它，需明确迁移/重置策略。

### 增加第三个维度（例如版型）

这不是只改 seed：domain.ts 的 Selection、options schema、resolveSku、前端控件、后端 options 输出和数据库唯一约束都固定为 colour/size。应把选项抽象成按维度 ID 的映射，并测试不完整选择、组合匹配与选项禁用。能指出这种限制比声称“完全通用”更可信。

### B 改成运费优先

更换 DP 比较对的顺序，并同步修改单调队列 key、转移、恢复目标判断和 oracle。不要只修改最终输出排序。新增一个“一仓库更贵、两仓库更便宜”的回归测试，确认目标顺序变化已生效。

### A 的重复 ID 必须校验 payload

这会改变题目当前协议。把 processed set 改为 event_id→规范化 payload/结果的字典；明确不同 payload 返回什么状态，再写测试。先说明这是新规则，不应在原题里偷偷加该行为。

### 增加多用户购物车

先建立身份/会话，再将 cart_items 主键改为 `(cart_id,sku_id)`，幂等作用域至少包含 cart_id，库存仍全局共享。不能直接相信客户端传来的任意 user_id/cart_id，否则会产生越权。它超出当前题目，但可以解释扩展边界。
